# Git 歴史操作

## 概要
コミット履歴を「なかったことにする・打ち消す・植え替える」3つの操作。それぞれ元のコミットへの影響と安全な使い所が異なる。

## 理解したこと

### reset・revert・rebase の使い分け

「コミット履歴を操作したい」ときの選択肢。

| | やること | 元のコミット | 安全な使い所 |
|---|---|---|---|
| `revert` | 打ち消すコミットを追加 | 残る | push後・共有ブランチでも安全 |
| `reset` | ブランチのポインタをずらす | 内部には残る（辿れなくなるだけ） | ローカルのみ・push前 |
| `rebase` | コミットを作り直して別の場所に植え替える | 新コピーが生まれる（元は残る） | ローカルのみ・push前 |

---

### reset の本質

reset はコミットを削除するのではなく、**ブランチが指すコミットIDをずらす操作**。

コミット自体はしばらくGit内部に残っているが「どこからも辿れなくなる」だけ。

```
A → B → C    ← git reset B を実行
A → B         ← Cはどこからも辿れなくなる
```

オプションで「ずらした後のワーキングディレクトリの状態」が変わる。

| オプション | 変更の残し方 |
|---|---|
| `--soft` | ステージングされた状態で残す |
| `--mixed`（デフォルト） | ステージングされていない状態で残す |
| `--hard` | 変更を破棄する |

ステージングをやめたいだけなら `git reset .`（ワーキングディレクトリの変更は残る）。

---

### rebase が禁忌になる理由

rebase は「ブランチの根元（ベース）を別の場所に植え替える」処理。コミットを作り直すため**コミットIDが変わる（C → C`）**。

```
（rebase前）A → B → C
（rebase後）A → B → C`  ← 親IDが変わりハッシュも別物
```

push後に rebase すると、リモートには元の C があるのにローカルは C` に変わっている。他の人は元の C を親として積み上げているため、push しようとすると歴史が噛み合わなくてコンフリクトが爆発する。

**ローカルかつ push 前なら便利**（分岐点を main の最新に揃えてログを直線化できる）。

---

### 主要コマンド

| コマンド | 説明 |
|---|---|
| `git revert コミットID` | 逆のコミットを追加して打ち消す |
| `git reset コミットID` | ブランチのポインタをずらす |
| `git rebase ブランチ名` | ブランチの根元を指定ブランチの先端に植え替える |
| `git reflog` | HEADの移動履歴を表示（操作ミス時の復旧に使う） |
