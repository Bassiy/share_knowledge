# 情報セキュリティの7要素

## 概要
セキュリティを考える際の基本的な観点。CIA(機密性・完全性・可用性)の3要素に、真正性・責任追跡性・否認防止・信頼性の4要素を加えた7つで構成される。

## 理解したこと

### CIA(基本3要素)

| 要素 | 意味 | 侵害の例 |
|--|--|--|
| 機密性 | アクセスを許可されていない侵入者がデータを閲覧・持ち出せてしまう状態にならないこと | 個人情報漏洩 |
| 完全性 | データが不正に書き換えられないこと | Webサイト改ざん、DNSエントリ改ざん |
| 可用性 | サービス提供が止まらないこと | DoS攻撃による意図的な集中アクセス |

DNSエントリが改ざんされると、正しいURLを入力しても攻撃者が用意した偽サイトのIPアドレスに誘導される(DNSキャッシュポイズニング等)。

見た目そっくりな偽サイトでログイン情報を盗まれる被害につながる。

---

### 拡張4要素

| 要素 | 意味 | 実現手段 |
|--|--|--|
| 真正性 | 利用者やデータの発信元が名乗っている通りの本物であること(なりすましでない) | 署名・認証 |
| 責任追跡性 | いつ誰が何をしたかを後から適切に追跡・追及できること | ログ |
| 否認防止 | 発生事象やデータを後から「なかったこと」にされないこと | タイムスタンプ・署名技術 |
| 信頼性 | システムの処理が適切で矛盾なく動作できる構成であること | ハードウェアの冗長化 |

---

### 完全性 と 真正性の違い(混同ポイント)

どちらも「改ざんされていないか」に関わるため混同しやすいが、見ている対象の軸が異なる。

| | 完全性 | 真正性 |
|--|--|--|
| 確認する対象 | データそのものの中身 | 利用者・発信元(誰が/どこから) |
| 典型的な技術 | ハッシュ | 署名(秘密鍵による暗号化) |

ハッシュ単体は「データが変わっていないか」を確認する完全性の道具であり、誰でも計算できるため単体では発信元を証明できない。

ハッシュ値を送信者だけが持つ秘密鍵で暗号化する(=デジタル署名)ことで初めて「本人が作った」ことの証明になり、真正性につながる。

使い方込みで真正性になる、という関係。

---

### 責任追跡性 と 否認防止の違い(痕跡と証拠)

真正性が「その時点での本人確認」なのに対し、責任追跡性・否認防止はどちらも事後に関わる要素。

両者の違いは「痕跡」か「証拠」かで整理できる。

| | 責任追跡性 | 否認防止 |
|--|--|--|
| 位置づけ | 痕跡(ログ) | 証拠 |
| 主な用途 | 社内的な調査・監査 | 対外的・法的な場面(電子契約・送金指示など) |
| 例 | DBのcreated_atのような改ざん可能なタイムスタンプ | TSA(第三者機関)が秘密鍵で署名した暗号学的タイムスタンプ |
| 弱点/強み | ログ自体が改ざんされうる、本人が否定する余地が残る | 秘密鍵がないと偽造できず本人も否定しにくい |

---

### 署名の内部処理(実装で気づいたこと)

「ハッシュ化」と「署名」は別の処理。ハッシュ化に鍵は使わない。

| ステップ | 処理 |
|--|--|
| 1 | messageをSHA256でハッシュ化(署名側) |
| 2 | ハッシュ値を秘密鍵で暗号化 → これが署名(signature) |
| 3 | messageをSHA256でハッシュ化(検証側、①と同じ処理) |
| 4 | signatureを公開鍵で復号 → ハッシュ値を復元 |
| 5 | ③と④のハッシュ値が一致するかを比較 |

メッセージを直接暗号化せずハッシュを挟む理由は2つ。

RSAの演算は重く、メッセージが長いほど遅くなる(速度)。

RSAは鍵サイズ(2048bit=256バイト)より大きいデータを直接暗号化できない(サイズ制限)。

ハッシュ化すれば可変長のmessageを常に固定長(32バイト)に圧縮できるため、この2つの制約を回避できる。

---

### 鍵・ハッシュ・署名の保管先(実務)

| 対象 | 保管先 | 理由 |
|--|--|--|
| 秘密鍵 | KMS・HSM・Vaultなどの専用鍵管理サービス | 漏洩するとなりすましが可能になる最重要機密のため、DBに平文で置かない |
| 公開鍵 | DB | 公開が前提のものなので制限不要 |
| 署名(signature) | DB(対象データと一緒に) | 後から本人が署名したものかを検証するため |
| ハッシュ値 | DB | 改ざんチェックや検索用途 |
