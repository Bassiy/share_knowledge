# ハッシュの決定性が目的で真逆の意味を持つ

## 捉えるもの
「同じ入力からは常に同じ出力が得られる」というハッシュの決定性は共通なのに、ドメインによって「衝突」への態度が正反対になる。同じ仕組みが、目的次第で「絶対避けるべき事故」にも「望ましい効率化」にも「前提とする仕様」にもなる。

## 3ドメインでの現れ方

### 衝突への態度が逆転する

| ドメイン | 出力空間と入力空間の関係 | 衝突への態度 | 目的 |
|---|---|---|---|
| セキュリティ | 出力空間が広く、衝突をほぼ起こさせない設計（衝突耐性） | 起きてはならない事故 | 改ざん検知 |
| Git | 同じ内容は同じ出力にしたい | 望ましい（意図的な使い回し） | 重複排除・同一性判定 |
| ロードバランサー | 出力空間を意図的に極小（サーバー台数）へ圧縮 | 前提・大量に発生する（多対1） | 決定的な振り分け |

---

### なぜ同じ性質がここまで分岐するか

決定性そのもの（同じ入力→同じ出力の保証）はどのドメインでも共通している。

分岐点は「入力空間に対して出力空間をどう設計するか」。

- 出力空間 ≫ 想定される入力の多様性 → 衝突がほぼ起きない前提で使える → 改ざん検知（セキュリティ）
- 出力空間が「内容の同一性」を表す → 同じ入力は意図的に同じ出力にまとめたい → 重複排除（Git）
- 出力空間 ≪ 入力の多様性（意図的に圧縮） → 大量の多対1が前提になる → 決定的な振り分け（ロードバランサー）

ロードバランサーのケースでは、衝突そのものより「その衝突（多対1の割り振り）が均等に分散しているか」が焦点になる。ハッシュ関数の出力が一様分布に近いほど、扱うIPの数が増えるにつれて各サーバーへの割り振りが均等に収束していく。
